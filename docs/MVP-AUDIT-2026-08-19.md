# BeautyMove — MVP Audit 2026-08-19

## Purpose

Establish a clean technical baseline before any further MVP feature work.

## Production rule

- `main` remains production.
- Agenda is frozen. No Agenda JS/CSS/HTML changes are permitted during this audit.
- No new Agenda fix/final/stable/correction layers may be added.
- Foundation work occurs on `foundation/mvp-audit-2026-08-19`.

## Executive findings

### Critical

1. Operational data is still primarily manipulated through `localStorage` in `app.js`, `data.js` and Agenda controllers, while Firestore is intended to be the persisted source of truth.
2. The application contains a large number of Agenda-specific scripts and styles with overlapping DOM responsibilities. Agenda is explicitly frozen and excluded from this workstream.
3. Professional and client operational experiences in `app.js` still use local demo/static data instead of a single backend data boundary.
4. Authentication has a local-session shortcut in `protectPage()`: when a matching local session exists, the page is allowed without revalidating the Firebase user/profile on every protected-page load.

### High

5. `cadastro.html` loads `auth.js`, `data.js` and `app.js`; `auth.js` owns registration while `app.js` also initializes registration/dashboard behavior. This is workable today but creates unnecessary ownership overlap.
6. Registration writes user data to Firestore and role data to `salons`, `professionals` or `clients`, but the rest of the application does not consistently read from those collections.
7. `app.js` contains duplicated state helpers (`readJson`, `getState`, `saveState`, `updateState`) instead of consistently using `BeautyMoveData`.

## Confirmed architecture gap

Current intended architecture:

`Firebase Auth + Firestore -> data boundary -> UI`

Current effective architecture in several MVP areas:

`Firebase Auth -> local session/profile -> localStorage operational state -> UI`

and, in parallel:

`Firestore -> registration/profile persistence`

This must be consolidated before expanding functionality.

## Non-Agenda workstream

The first stabilization target is the shared data boundary and authentication/session behavior. The objective is to make non-Agenda pages use one predictable source of truth without changing the frozen Agenda.

## Acceptance gates

Before any non-Agenda change reaches `main`:

- registration creates Auth + correct role document;
- login restores the correct role;
- protected pages do not trust a stale local session as authority;
- profile reads come from Firestore when Firebase is enabled;
- operational data access is centralized behind `BeautyMoveData`;
- no regression is introduced in the frozen Agenda files;
- JavaScript syntax checks pass;
- browser regression checks are performed on access, registration and role dashboards.

## Current decision

Do not modify Agenda. Consolidate shared application state and authentication first.
